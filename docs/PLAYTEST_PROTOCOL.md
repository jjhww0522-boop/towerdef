# 실제 이용자 플레이테스트 절차

작성일: 2026-09-19. 현재 모집·참여 인원 **0명**, 실제 응답·관찰 자료 **없음**. 아래는 실행 계획이며 결과가 아니다. [내부 검토](USABILITY_REVIEW.md)와 실제 이용자 자료를 구분한다.

## 먼저 4명, 이후 30명

| 단계 | 참가·환경 | 목적과 종료 조건 |
| --- | --- | --- |
| 파일럿 | 게임을 처음 접하는 실제 4명, 한 명씩 약 20분. 각자 새 방, 1배속 | 혼자 설명 없이 조작하는지 관찰. 막힌 기능을 수정하고 같은 과제로 재검사 |
| 협동 확인 | 실제 4명이 각자의 화면과 입력을 동시에 사용 | 파견의 부담·공동 보상·동료 상황을 이해하는지 확인. 네 브라우저를 에이전트가 조작한 결과는 이 단계의 대체물이 아님 |
| 확대 | 목표 이용자 30명 이상, 각 3판 이상. 첫 경험자·장르 경험자를 구분 | 첫 판 학습과 후속 판 변화 비교. 4인 편성을 위해 모집 인원은 32명으로 늘릴 수 있음 |

현재 서버는 `127.0.0.1`에만 연결된다. 파일럿은 개발 PC의 로컬 브라우저에서 순차 진행할 수 있다. 여러 기기를 쓰는 협동 시험은 연결 환경이 준비된 뒤 실행하며, 문서만으로 LAN·원격·iPhone 지원이 완료된 것으로 취급하지 않는다. 첫 접속부터 진행되는 현재 연습방과 4명이 모여 시작하는 정식 경기 목표도 구분한다.

파일럿 4명은 비율을 확정하기 위한 표본이 아니다. 각 과제의 성공 인원과 관찰 사례를 그대로 기록한다. 같은 사람이 수정 전후로 반복했다면 신규 이용자의 첫 경험으로 다시 집계하지 않는다.

## 진행 전 준비

1. 진행자는 `npm test`를 확인하고 `npm run dev`로 브라우저 버전을 연다. 참가자 없이 먼저 소환·조합·강화·파견·결과·새 방 시작을 점검한다. 아직 구현되지 않은 버튼이나 기록 항목은 시험 완료로 표시하지 않는다.
2. 빌드 식별자, 콘텐츠 버전, 날짜, 화면 크기, 브라우저, 배속, 참가 인원을 기록한다. 파일럿은 1배속으로 통일한다. 3·6배속은 내부 기능 검사 자료로 따로 둔다.
3. 참가자 ID는 `P01` 같은 임의 번호를 쓴다. 진행자는 게임을 처음 해보는지와 장르 경험만 기록한다. 실명·연락처·인증 토큰은 피드백 파일에 넣지 않는다.
4. "미완성 게임의 조작을 확인합니다. 어려운 부분은 제품을 고칠 단서입니다. 원하면 언제든 멈출 수 있고, 의견은 이 기기에 기록합니다"라고 안내한다. 화면·음성 녹화는 참가자가 동의한 경우에만 한다. 이 절차는 모집 메시지 발송이나 녹화를 실행한 기록이 아니다.
5. 진행자는 버튼 위치나 정답을 먼저 알려주지 않는다. 생각을 말하도록 강요하지 않고, 멈춘 때와 선택 이유를 짧게 확인한다. 정답 설명은 해당 과제를 종료한 뒤 한다.

## 참가자용 과제와 관찰

과제는 한 번에 하나씩 전달한다. UI의 안내는 이용할 수 있지만 진행자가 버튼을 지목하면 `assisted`로 기록한다. 기술 장애는 사용자의 이해 실패와 분리한다.

| 순서 | 그대로 읽을 과제 | 관찰·완료 기준 |
| --- | --- | --- |
| 1 — 소환 | "내 전장을 지킬 유닛을 한 기 마련해 보세요." | 클릭 전후 금화와 유닛 변화를 알아보는지. 첫 행동까지 실제 초, 불필요한 클릭, 완료 여부 기록 |
| 2 — 조합 | "화면에서 만들고 싶은 장수를 하나 골라, 필요한 재료를 확인하고 만들 수 있게 되면 만들어 보세요." | 재료 확보 전에는 부족한 재료를 찾는지 관찰. 재료가 갖춰져 조합 가능 표시가 처음 나온 때부터 성공까지 측정. 무작위 소환 때문에 끝내 기회가 없으면 `not_reached`이며 실패로 단정하지 않음 |
| 3 — 강화 | "지금 가진 유닛을 강화해 보세요. 어떤 유닛에 적용될지 먼저 설명해 주세요." | 선택한 태그의 실제 보유 유닛 1기 이상과 미적용 대상의 차이를 설명하는지. 금화가 부족하면 시점과 이유를 기록하고 가능한 때 다시 제시 |
| 4 — 파견 | 스토리 개방 시 "공동 스토리에 참여해 보세요. 참여하는 동안 내 전장이 어떻게 될지 설명해 주세요." | 최대 2기 선택·파견, 개인 전장에서 빠짐, 종료 후 복귀를 알아보는지. 스토리 실패와 개인 패배를 같은 일로 이해하는지도 결과 후 확인 |
| 5 — 결과·재도전 | 결과 후 "방금 판에서 무슨 일이 있었는지, 화면을 보고 설명해 주세요." | 패배·클리어 원인과 다음에 바꿀 선택을 기록. 이후 "더 플레이하거나 여기서 마쳐도 됩니다"라고 동일하게 안내하고 자발 선택을 관찰 |

한 과제에서 60초 동안 진행이 멈추면 "지금 무엇을 하려고 하셨나요?"를 먼저 묻고 관찰을 기록한다. 계속 막히면 그 과제를 `assisted`로 끝낸 후 다음 과제로 이동할 최소 도움을 준다. 자원·스토리 개방을 기다리는 시간은 조작 정체와 구분한다. 패배해 다음 과제에 도달하지 못하면 `not_reached`로 남기고, 별도 안내 세션에서 확인한다. 안내 세션 결과를 첫 판 독립 성공으로 바꾸지 않는다.

협동 시험에서는 파견 여부를 각자 정하게 하고, 동료끼리 대화해도 된다. 진행자가 누가 어떤 장수를 파견할지 정해주지 않는다. 동료 지원을 알아본 순간, 참여하지 않은 이유, 대박 소환을 다른 사람이 실제로 인지했는지를 기록한다. 1인 파일럿으로 협동 재미를 결론내리지 않는다.

## 종료 질문

- "어느 순간 다음에 무엇을 해야 할지 가장 불분명했나요?"
- "이번 판의 결과에 영향을 줬다고 생각하는 선택은 무엇인가요?"
- "조합과 소환의 결과가 각각 어떻게 정해진다고 생각하나요?"
- "파견 중인 유닛은 어디서 싸우며, 스토리가 실패하면 어떤 일이 생기나요?"
- "계속하거나 멈추기로 한 이유는 무엇인가요?"

"재미있었죠?", "다음에도 하실 거죠?" 같은 동의를 유도하는 질문을 하지 않는다. 선택형 점수를 쓰더라도 이유와 실제 행동을 함께 기록하고, 의향을 재도전 행동으로 집계하지 않는다.

## 지표 정의와 해석

| 항목 | 집계 방법 | 내부 가설 |
| --- | --- | --- |
| 첫 조합 독립 수행 | 첫 판 조합 기회가 있었던 참가자 중, 진행자 도움 없이 처음 조합을 완료한 인원 / 기회가 있었던 인원. 전체 참여 인원·기회 미도달 수도 별도 공개 | 80% 이상을 검토 기준으로 시작. 시장 기준이나 현재 성과가 아님 |
| 패배 후 자발 재도전 | 첫 판 개인 패배 후 추가 플레이를 요구받지 않은 참가자 중, 60초 이내 새 판을 시작한 인원 / 재도전 선택을 할 수 있었던 개인 패배 인원 | 60% 이상을 내부 가설로 시작. 시간 부족·기술 장애·클리어는 별도 기록 |
| 규칙 이해 | 소환은 무작위, 조합은 정해진 재료, 강화는 태그 적용, 파견은 개인 방어에서 제외·복귀를 각자 설명했는지 | 정답 항목 수와 오해 원문 기록. 하나의 만족도 점수로 합치지 않음 |
| 학습 변화 | 동일 참가자의 1·2·3판 과제 시간, 도움 횟수, 선택 이유 변화 | 배속·버전·동료 구성 변화와 함께 해석 |

확대 시험의 "각 3판" 안내가 재도전을 강제할 수 있다. 첫 판의 자발 선택은 후속 2판 과제를 요청하기 전에 따로 관찰하고, 진행자가 2판째를 요청한 경우 `prompted`로 분리한다. 3판을 모두 끝낸 사람만 남겨 재도전율을 계산하지 않는다. 분모가 0이면 비율은 "자료 없음"으로 적는다.

## 로컬 기록과 개선 루프

브라우저의 로컬 피드백 저장·내보내기를 사용하되, 현재 구현된 항목은 화면과 내보낸 파일로 확인한다. 관찰표는 아래 열로 로컬에 작성할 수 있다. 외부 서비스로 자동 전송하지 않는다.

```text
source: actual_participant | agent_heuristic | scripted_simulation
participantId, sessionId, buildId, contentVersion, playbackSpeed
taskId, startedAtRealMs, endedAtRealMs
result: success | assisted | failed | not_reached | technical_block
observation, participantQuote, retryChoice: started | stopped | prompted | unavailable
```

`participantQuote`는 실제 발언을 기록했을 때만 채운다. 의견을 작성한 사람의 자기보고와 진행자가 직접 본 행동은 `observation`에서 구분한다. 세션 토큰 대신 별도 비밀이 아닌 시험 번호를 `sessionId`로 사용한다.

한 회차가 끝나면 관찰 → 원인 가설 → 최소 수정 → 같은 과제 재검사의 연결을 남긴다. 우선순위는 진행 불가·상태 유실, 잘못 이해해 손해 보는 선택, 정보 탐색의 불편 순서다. 작은 파일럿의 한 사례는 문제 후보로 다루되 확정적인 소비자 선호로 표현하지 않는다. 공개 배포·유료 구매·참가자 모집은 준비 절차와 구분하며 아직 실행하지 않았다.
