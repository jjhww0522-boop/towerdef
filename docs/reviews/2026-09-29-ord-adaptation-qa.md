# 원랜디 참고 개편 — 독립 QA

2026-09-29. 담당: 기획 조사와 분리하여 서버·클라이언트 소스를 편집하지 않은 QA 에이전트. 범위는 솔로/협동 입장, 엔진 비용, 세션 복구, 개인 전장 격리, 협동 파견·보상과 웹/네이티브 모드 계약이다.

## 결과

**검토 범위에서 재현 가능한 새 결함을 찾지 못했다.** 기존 통합 검사를 반복하지 않고 코드 검토와 추가 HTTP 경계 확인을 수행했다. 이 결과는 실물 모바일·상용 멀티 서버 검증 완료라는 뜻이 아니다.

### 읽기 전용 검토

- `server/core/index.ts`: 명시적 모드, 개인전 인원 제한, 솔로 스토리 제거/파견 거절, 개인 결과에 모드 기록. 공격·EMP·시설 피해 대상이 해당 플레이어의 적 목록 안에 있으며 공동 스토리는 별도 대상이다. 파견 로봇은 같은 슬롯을 차지하며 본진 공격에서 빠진다.
- `tools/dev-server.mjs`: 잘못된 모드, 기존 방과 모드 불일치, 솔로 추가 참가 거절이 `consumeEngine` 이전이다. 기존 참가자는 엔진을 다시 쓰지 않고, mode 생략 요청은 기존 방의 실제 모드를 유지한다. 새로운 mode 생략 요청은 이전 클라이언트 호환으로 coop이다.
- `server/protocol.ts`: 상태에 서버 mode를 전달하고 결과에도 mode가 남는다. 솔로의 stories는 빈 배열이다.
- `playtest/app.js`: 새 출발은 선택 모드, 재도전은 현재 서버 상태의 모드를 사용한다. mode가 없는 이전 웹 세션은 상태 조회로 복구하고, 실제 반환 모드를 세션에 저장한다. 파견/팀 UI는 협동에 제한한다.
- C# `LocalSession`, `Protocol`, `MobileModel`, `BattleClient`: 새 입장/저장 중인 입장 요청/재도전의 mode 전달을 확인했다. 훈련 요청은 solo로 보정한다. 이전 DTO의 mode 생략은 coop 호환이며 실제 훈련 상태는 협동 UI로 보지 않는다. 이 검토는 Unity 실행 검사가 아니다.

### 추가 HTTP 경계 확인: 7개 통과

실행 방식: 기존 `createDevServer`를 루프백 임시 포트에 열고 `createProgressionStore` 메모리 프로필 3개, `automaticTicks:false`로 검사했다. 실제 `/profile`, `/session`, `/action`, `/state` 요청을 사용했다. 시간은 첫 스토리 직전으로 이동했으며, 파견 가능한 `laser_4`를 테스트 데이터로 주입하고 마지막 스토리 HP를 1로 설정했다. 자연 플레이 난이도 실험이 아니라 입장/퇴장/보상 경계만 고립한 검사다. 파일 기반 실제 계정은 수정하지 않았다.

| 확인 | 결과 |
| --- | --- |
| 첫 참가자의 스토리가 진행 중일 때 두 번째 참가자 입장 | mode coop 유지, 엔진 5→4 |
| 첫 참가자가 로봇 파견 뒤 떠남 | 로봇 파견 상태 해제, 결과 mode coop, 이후 공동 고철 보상 제외 |
| 남은 후발 참가자가 파견하여 스토리 완료 | 공동 고철 보상 정확히 1회, 로봇 본진 복귀 |
| 스토리 성공 직후 세 번째 참가자 입장 | 초기 고철만 보유, 이미 끝난 스토리 보상 소급 없음, 엔진 1회 소모 |
| 완료 후 상태 3회 조회 | 공동 고철 추가 지급 없음 |
| 같은 참가자/방 재입장 | mode coop·기존 원정 유지, 엔진 추가 차감 없음 |
| 기존 방에 solo로 재입장, 구버전 콘텐츠 메타데이터 요청 | 각각 mode_mismatch/version_mismatch 거절, 엔진 변화 없음 |

재현 순서: 메모리 서버 시작 → host coop 입장 → 첫 스토리 직전 tick으로 이동해 1tick → guest 입장 → host 파견/leave → guest 파견/HP 1에서 1tick → 세 번째 계정 입장 → 반복 state → guest 재입장 → 잘못된 mode/contentVersion 입장. 각 단계의 상태·고철·엔진·결과 mode를 assert로 검사했다. 실행 exit code 0.

## 재사용한 통합 근거

대장/구현 담당이 완료했다고 전달한 Node 293개, C# 계약 20개, 모드 브라우저 18개, 89경기 전투 감사 결과를 재실행하지 않았다. 세부 전투 수치는 [통합 플레이 기록](../playtests/2026-09-29-ord-adaptation.md)을 따른다. 화면 투영·튜토리얼 터치·팝업 비율은 별도 담당의 검증 영역이다. 이 문서의 추가 직접 실행은 위 HTTP 경계 확인뿐이다.

## 남은 한계

- Nakama는 기존대로 4인 연습 방 생성 경로를 사용하며 이번 변경은 mode coop을 명시하는 수준이다. 로컬 HTTP 모드 구분을 Nakama의 개인전 매치메이킹·상용 보상 지원으로 확대 해석하지 않는다.
- 협동 도중 후발 입장은 방의 현재 시간에 합류한다. 초반 자원으로 늦게 합류할 때의 생존성·대기방 설계는 이번 변경으로 새로 해결되지 않았다.
- 실제 사람의 만족도·인기 버전 선호, 실물 iPhone/Android, Unity Editor, WAN 지연·연결 끊김을 이 독립 QA에서 측정하지 않았다.
- 원랜디의 실제 맵 크기·유닛 간격·몹 속도를 실측하여 복제한 구현이 아니다. 외부 근거의 범위는 [조사 기록](../reference/2026-09-29-ord-research.md)에 분리했다.
