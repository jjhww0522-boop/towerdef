## 2. 사용자 의도와 현재 요청 범위

사용자는 초기 아이디어 토론을 마친 뒤, 에이전트가 게임회사 제작 책임자처럼 필요한 페르소나 팀을 구성해 자율적으로 완성도 있는 게임을 만들도록 요청했다. 이후 집에서도 이어갈 수 있게 이 GitHub 저장소에 문서를 등록하고 푸시하는 일을 먼저 요청했다.

**최신 방향 수정:** 사용자는 2인이 아니라 4인 이상 협동을 원하며, 가능하면 8인과 그 이상을 희망한다. 첫 완성본은 4인으로 맞추고, 8인 이상은 구조상 확장 여지를 두되 실제 검증 후 지원한다. 오래된 2인 출시안을 그대로 구현하지 않는다.

이번 커밋은 그 인계를 위한 것이다. 다음 개발 세션에서는 실제 게임 제작을 이어갈 수 있다. 통상적인 설계나 코드 수정마다 재승인을 요구하지 말되, 외부 계정 사용·비용·공개 배포 등에 필요한 정보나 권한은 확인한다.

초기 토론은 계획 모드에서 이루어져 구현이 없었다. **계획 모드라는 상태를 프로젝트의 영구 제약으로 취급하지 말 것.** 다음 세션에서는 그 세션에 실제로 적용되는 지침과 사용자 요청을 따른다.

## 4. 기술 기본안

| 영역 | 선택안 | 책임 |
| --- | --- | --- |
| 게임 클라이언트 | Unity 6.3 LTS의 지원되는 패치, C# | 터치 입력, 전투 표현, 애니메이션, UI, 사운드 |
| 코드 편집 | VS Code와 Microsoft Unity 확장 | C# 편집·디버깅 |
| 게임 서버 | Nakama, TypeScript | 소환·합성·강화·전투·스토리·승패의 최종 판정 |
| 영구 저장 | PostgreSQL | 계정 진행, 레시피 해금, 결과 및 지급 기록 |
| 공유 콘텐츠 | 저장소에서 관리하는 JSON 데이터 | 유닛·레시피·웨이브·확률·비용의 단일 원본 |
| 로컬 서버 실행 | Docker Compose | Nakama와 PostgreSQL 개발 환경 |
| iOS 빌드 | Mac + Xcode 또는 Unity Build Automation | 서명된 아이폰 앱 빌드 |

Unity는 화면과 입력을 맡고, 승패에 영향을 주는 규칙은 TypeScript 서버 코어 한 곳에 구현한다. C#에 별도의 권위 있는 전투 계산을 중복 구현하지 않는다. 로컬 연습과 자동 밸런스 실험도 같은 규칙 코어를 사용한다.

고정 경로와 자동 전투를 전제로 서버는 10Hz 갱신에서 시작하고, Unity에서 표시를 부드럽게 보간한다. 실제 성능을 측정한 뒤 주기를 조정한다. 세부적인 물리 시뮬레이션을 요구하는 게임으로 확장하면 이 선택을 다시 검토한다.

플레이어는 ID를 기준으로 한 목록으로 관리하고 경기 인원과 UI 슬롯을 2인으로 고정하지 않는다. 첫 정식 매치는 4인으로 설정한다. 8인 검증에서는 서버 전투 부하뿐 아니라 전송량과 다수 전장 표시 비용도 측정한다. 클라이언트는 내 전장과 선택한 상세 화면을 중심으로 표시하며, 나머지는 상태 요약을 사용한다.

Nakama의 TypeScript 코드는 해당 런타임 제약에 맞춰 빌드한다. Node 전용 API를 서버 런타임에서 사용할 수 있다고 가정하지 않는다. Node는 개발 도구·컴파일·자동 테스트에 사용한다.

콘텐츠 데이터는 검증 후 서버와 클라이언트에 배포한다. 프로토콜·콘텐츠 버전이 맞지 않는 클라이언트는 입장 전에 업데이트하도록 한다.

## 5. 온라인과 저장에서 지킬 기준

- 소환 결과, 자원 소비, 조합 재료, 유닛 소유권, 강화, 파견과 보상을 서버가 검증한다.
- 클라이언트는 행동 요청을 보내며, 희귀 유닛이나 클리어 결과를 스스로 확정하지 않는다.
- 요청 순번으로 재전송된 행동을 중복 실행하지 않도록 한다.
- 재접속은 인증된 기존 참가자에게 서버의 전체 현재 상태를 보내 복구한다.
- 접속이 끊긴 플레이어의 개인 방어도 시간 정지 없이 진행한다. 동료의 이탈이 남은 사람의 게임 프로세스를 종료하지 않게 한다.
- 지급 기록의 키는 경기와 플레이어를 식별하도록 구성한다. 결과 기록·해금·전적 갱신은 재시도해도 중복 지급되지 않는 원자적 저장으로 처리한다.
- 클라이언트가 영구 진행이나 구매·보상 기록을 직접 수정하지 못하게 한다.
- 서버 프로세스 장애 후 진행 중인 판 전체 복원은 첫 버전의 약속에 포함하지 않는다. 이미 확정·저장된 보상은 다시 조회할 수 있어야 한다.
- 비밀번호, 토큰, 서버 키, 인증서, 프로비저닝 파일은 Git에 넣지 않는다. 구현 시 `.gitignore`와 비밀 값이 없는 환경 설정 예제를 먼저 준비한다.

## 6. 구현 순서와 완료 조건

### A. 환경 준비와 데이터 명세

1. 실제 PC의 Unity·Node·Docker와 기기 준비 상황을 점검한다.
2. 지원 버전을 고정해 클라이언트·서버·공유 데이터의 최소 작업 구조를 만든다.
3. 초기 유닛·조합·강화·소환·웨이브 데이터와 프로토콜을 작성한다. 처음에는 소수 유닛으로 검증하고 전체 27종으로 확장한다.
4. 필요한 장수 분류나 세부 수치는 위임된 범위에서 결정하고 설계 문서에 반영한다.

완료 조건: 새 환경에서 문서만 따라 개발 서버를 실행하고, 데이터의 잘못된 참조나 성립하지 않는 조합을 검출할 수 있다.

### B. 한 판의 핵심 전투

랜덤 소환 → 확정 조합 → 태그 강화 → 개인 웨이브 → 최종 보스 → 승패를 연결한다. 임시 아트를 사용하되 게임 상태와 화면 표현을 분리한다.

완료 조건: 같은 입력과 테스트용 난수로 결과를 재현하고, 소환·합성·강화의 자원 오류와 이중 실행을 막는다. 클리어가 불가능한 해금 순환이 없어야 한다.

### C. 4인 협동과 공동 스토리

두 클라이언트의 초기 연결부터 점검하고, 네 실제 클라이언트의 방 입장, 대박 소환 표시, 스토리 파견·복귀·보상, 개인 패배와 관전, 재접속으로 확장한다. 사회성이 핵심이므로 싱글 전투를 장기간 완성한 뒤 온라인을 덧붙이지 않는다.

완료 조건: 4인 경기에서 한 명 또는 여러 명의 이탈에도 남은 사람의 판이 이어지고, 각 화면과 서버의 자원·유닛·스토리 상태가 일치한다. 스토리 실패는 개인 즉시 패배로 이어지지 않는다. 8인 시뮬레이션으로 확장 병목도 기록하지만, 이것만으로 실제 8인 플레이 검증을 대신하지 않는다.

### D. 아이폰과 영구 진행

아이폰 터치·화면·성능을 검증하고, 튜토리얼·초대·매칭·클리어 저장·레시피 해금·계정 관리를 연결한다.

완료 조건: 실제 아이폰에서 튜토리얼부터 한 판과 첫 해금까지 플레이하고, 앱 재실행 후 진행이 유지된다. 영구 기록은 서버에서 확인한다.

### E. 첫 출시 콘텐츠와 표현 완성

3전장·2난도·27유닛을 기준으로 독자적인 아트·효과음·음악·스토리 연출을 완성한다. 설정에는 음량·진동·연출 수준과 계정 관리 등 실제 필요한 기능만 포함한다.

완료 조건: 임시 자산이 남지 않고 출처·이용 조건을 추적할 수 있다. 처음 보는 사람이 게임 안의 안내로 소환·조합·강화·파견을 이해할 수 있다.

### F. 베타와 배포 준비

실제 이용자 테스트로 조작 이해, 재도전, 협동의 가치, 운과 판단의 관계를 검증한다. 스토어 설명·스크린샷·개인정보 처리·계정 삭제·지원 연락처·배포용 빌드를 준비한다.

완료 조건: 아래 검증 기준을 충족하고 필요한 외부 계정과 배포 권한이 갖춰진 상태에서 테스트 배포·출시를 진행한다. 페르소나의 의견이나 자동 시뮬레이션만으로 실제 재미를 검증했다고 하지 않는다.

## 7. 필요한 검증

### 규칙과 데이터

- 고정 난수와 행동 순서로 전투를 재현한다.
- 부족한 자원·재료, 다른 사람 유닛 조작, 같은 요청의 반복을 거부한다.
- 조합 재료는 정확히 한 번 소비하고, 합성 결과는 정확히 한 번 생성한다.
- 태그가 맞는 강화만 적용하며, 파견 중에도 소유자의 강화가 일관되게 반영된다.
- 기본 레시피만으로 보통 전장의 첫 클리어가 가능하고, 해금이 순환 의존하지 않는다.
- TypeScript 단위 테스트 외에 실제 Nakama 런타임에서 실행되는 통합 테스트를 포함한다.

### 멀티플레이와 저장

- 네 클라이언트의 동시 파견, 빠른 스토리 성공, 시간 종료, 개인 패배 시 복귀·제외를 검증한다.
- 4인과 8인의 최대 유닛·적 수에서 서버 처리 시간, 지연 누적, 전송량, 클라이언트 성능을 각각 측정한다. 8인 활성화 전에는 실제 다인 플레이도 별도로 검증한다.
- 200ms 지연, 5% 손실, 30초 단절, 120초 유예 종료와 백그라운드 복귀를 시험한다.
- 중복 클리어 요청, 저장 직전 연결 종료, 동시 진행 갱신에서 중복 보상·해금 유실이 없어야 한다.
- 남은 사람의 개인 판정이 동료 접속 여부 때문에 즉시 실패하지 않아야 한다.

### 실기기와 실제 이용자

- 지원 최저 아이폰을 결정한 뒤, 최대 전투 부하로 30분 실행하며 지속 30fps를 초기 목표로 측정한다.
- 메모리 증가, 발열, 배터리와 UI 가독성을 실제 기기에서 확인한다.
- 같은 해금·난도·난수 조건의 전략 비교와 실제 사람의 숙련 전후 플레이를 함께 본다.
- 초기에 실제 목표 이용자 30명 이상, 각 3판 이상을 목표로 검증한다. 모집은 아직 이루어지지 않았다.
- 첫 조합을 도움 없이 수행하는 비율 80%, 패배 후 자발적 재도전 60%를 내부 가설로 둔다. 시장 평균이나 성공 보장 수치로 설명하지 않는다.
- 기록 유실과 치명적인 연결 오류는 출시 차단 항목이다. 조작 이해나 재도전이 기대에 못 미치면 콘텐츠 양보다 규칙과 안내를 먼저 수정한다.

## 8. 아이폰 배포의 외부 준비사항

Windows에서도 Unity 프로젝트와 서버 개발은 가능하다. 로컬 iOS 최종 빌드는 macOS의 Xcode가 필요하며, Mac을 사용할 수 없다면 Unity Build Automation을 기본 후보로 검토한다.

- Mac 사용 가능 여부는 아직 미확인이다. 클라우드 경로는 장비 보유 사실을 대신하는 가정일 뿐, 구매·가입 완료 상태가 아니다.
- Xcode의 개인 기기 테스트와 TestFlight·App Store 배포는 계정 조건이 다르다.
- TestFlight와 App Store를 위해 Apple Developer Program, 서명 인증서·프로비저닝, App Store Connect 설정이 필요하다.
- Apple 개발자 계정의 현재 안내 가격은 연 99 USD 또는 지역 통화 금액이다. 진행 시 최신 조건을 다시 확인한다.
- 서버와 클라우드 빌드 비용은 별도이며 예산 승인은 아직 없다. 유료 가입이나 인프라 구매를 완료한 것으로 가정하지 않는다.
- 실제 iPhone, 플레이테스터, 지원용 연락처와 개인정보 처리 주체도 필요하다.

## 9. 제작 역할

| 역할 | 책임 |
| --- | --- |
| 제작 책임자 | 범위·우선순위·팀 작업 통합, 실제 완료 여부 판단 |
| 게임 디렉터 | 유닛·조합·난도·스토리와 밸런스 데이터 |
| 기술 디렉터 | 서버 판정·클라이언트·저장·빌드 구성 |
| UX·아트 담당 | 작은 화면의 구분성, 조합 안내, 캐릭터·연출 |
| 프로듀서·QA | 인계 재현성, 테스트, 외부 준비사항, 출시 기준 |

여러 에이전트를 쓰면 독립된 작업 범위를 명시하고 같은 파일을 동시에 수정하지 않도록 조율한다. 통합 담당자가 변경과 검증 결과를 확인한다.
