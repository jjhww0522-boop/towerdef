# 폐품로봇 원정대 — AI 개발 조직과 업무 운영

사용자 요청일: 2026-09-26. 사용자가 업무를 지시하면 총괄 대장이 판단해 필요한 팀에 배분하고 완료까지 통합한다. 이 문서는 이 저장소의 이후 작업에 공통 적용한다.

## 조직: 총괄 대장 + 6개 팀

사용자는 프로젝트 대표로 방향과 우선순위를 제시한다. 주 에이전트가 **총괄 대장**으로서 범위·일정 순서·담당·완료 기준을 정하고, 팀의 상충하는 제안을 판단하며 최종 결과를 책임진다. 팀 선택과 내부 작업 조율을 사용자에게 떠넘기지 않는다.

이는 반복 사용 가능한 AI 역할이다. 각 팀에 상시 실행 중인 직원이나 프로세스가 있다는 뜻은 아니다. 현재 세션은 대장을 포함한 동시 실행 슬롯이 4개이므로 최대 3개 작업팀을 병렬 투입하고 나머지는 순서대로 진행한다. 이후에는 실제 도구가 제공하는 제한을 따른다.

## 요청을 처리하는 순서

1. **대장 판단:** 사용자의 목적과 완료 조건을 정리한다. 작은 수정은 직접 처리하고, 나눠서 진행할 이점이 있는 업무에 필요한 팀만 배정한다.
2. **업무 배분:** 아래 작업 카드로 범위·소유 파일·의존 관계를 전달한다. 새 서식 파일을 매번 만들 필요는 없으며 에이전트 지시 메시지로 충분하다.
3. **설계와 구현:** 계약이 필요한 변경은 먼저 합의한다. 서로 독립적인 화면·서버·자산 작업은 병렬로, 결과에 의존하는 작업은 순서대로 진행한다. 검증팀은 구현 중에도 확인 시나리오를 준비할 수 있다.
4. **검증과 수정:** 구현 담당이 관련 검사를 수행한다. 주요 전투 규칙·경제·저장·협동 동기화·핵심 입력 변경은 독립 QA를 추가한다. QA는 우선 읽기 전용으로 재현·증거·영향을 보고하고, 대장이 수정 담당을 정한다.
5. **통합과 보고:** 대장이 결과를 검토하고 필요한 수정까지 마친다. 커밋·병합·릴리스 통합 담당은 작업별로 한 명을 정한다. 완료 여부와 필요한 검증을 확인해 사용자에게 하나의 결과로 보고한다.

### 작업 카드

```text
팀 / 작업명:
목표와 범위:
수정 소유 파일 / 읽기 전용 영역:
선행 작업과 공유할 계약:
완료 기준:
결과: 변경점 / 확인 증거 / 미검증 항목·남은 문제
```

팀은 배정 범위 밖의 대규모 변경이나 별도 프로젝트를 임의로 시작하지 않는다. 다른 팀 파일의 변경이 필요하면 대장에게 전달한다. 같은 파일을 두 팀이 동시에 수정하지 않는다. 기획의 수치 제안과 실제 콘텐츠 파일 편집도 구분해 편집자를 지정한다.

## 자주 들어올 요청의 배분 예시

| 사용자 요청 | 주 담당 | 협업·검증 |
| --- | --- | --- |
| “3스테이지를 5분, 난이도 2로 만들어” | 기획·밸런스 | 서버 적용, 클라이언트 시간·설명, QA의 시간·난이도 비교 |
| “유닛 클릭창이 버튼을 가려” | 클라이언트·UI/UX | 핵심 입력에 영향이 있으면 QA의 터치·회전 검증 |
| “같은 유닛 3개로 진화하게 바꿔” | 기획·밸런스 → 서버·전투시스템 | UI 재료 표시, 아트 가족 외형, QA의 재료 소모·저장·만칸 실험 |
| “타격감을 더 살려” | 아트·사운드 + 클라이언트·UI/UX | QA의 피격 일치·성능·움직임 줄이기 확인 |
| “친구와 하면 돈이 복사돼” | 서버·전투시스템 | QA의 동시 요청·재접속 재현, 필요시 출시·운영의 배포 점검 |
| “회사에서 이어하게 마무리해” | 출시·운영 | 각 담당의 미완료 사항 취합, 대장의 통합·검증·인계 |

## 판단과 검증 원칙

- **기획과 실행:** 기획팀이 재미·목표 난이도를 정의하고 서버/클라이언트팀이 실제 동작을 만든다. QA는 결과를 독립적으로 확인한다. 의견이 충돌하면 근거와 비용을 비교해 대장이 결정한다.
- **난이도:** [게임 공통 1~10 척도](design/DIFFICULTY_SCALE.md)를 따른다. 첫 두 구역은 난이도 1/1.5와 최대 3분/총 4분을 기준으로 한다. 조합·경제·적 압박을 한 번에 바꾸어 원인을 잃지 않게 실험을 나눈다.
- **실제 반응과 가설:** 초보자·숙련자·프로게이머 관점의 에이전트 평가는 가설이다. 실제 사람의 인터뷰·반응·만족도라고 부르지 않는다. 사람 검증이 있으면 참가 인원과 방법을 별도로 기록한다.
- **증거:** 밸런스는 시드·정책·해금 조건을, 성능은 기기·실행 환경·측정 조건을 남긴다. 봇의 행동이 사람과 다른 부분을 밝힌다. 기존 검사 결과는 변경 범위에 여전히 유효하면 재사용한다.
- **권한:** 기존 사용자 승인 범위 안의 일상 개발·테스트·수정은 진행한다. 팀 배정이 결제·개인정보 제공·파괴적 작업·외부 발행/연락의 별도 권한을 만들지는 않는다. 상위 지침과 기존 승인을 확인하고, 꼭 필요한 판단 요청은 준비된 결과와 함께 제시한다.
- **진행 보고:** 큰 작업을 시작할 때 투입 팀과 목적을 짧게 알린다. 최종 보고는 적용 내용·검증 결과·남은 문제를 중심으로 한다. 실제 실행하지 않은 팀의 검토나 테스트를 수행했다고 말하지 않는다.

## 역할 파일 사용 방법

`AGENTS.md`가 이 운영 방식을 연결한다. 대장은 해당 팀의 `.cursor/agents/*.md`를 읽고 실제 사용 가능한 에이전트 도구에 역할과 작업 카드를 전달한다. 파일이 있다는 이유로 도구가 자동 등록·실행한다고 가정하지 않는다. 기존 작업자를 재사용할 때도 현재 역할·범위를 새로 전달한다. 작업이 끝나면 결과를 수합하며 상시 실행이나 사용자 부재 중 별도 스케줄 실행을 주장하지 않는다.
